# ML_IMPLEMENTATION.md
## Industrial Emission Leak-Point Detector & Circular Alternative Recommender

---

## 1. ML Objective

Given a facility's leak-point profile (category, scale, industry, contribution), rank a curated set of circular-economy interventions by suitability — better than a flat rule lookup, while remaining explainable and safe to fall back away from.

## 2. Why ML Is Required (and Where It Is NOT)

The emissions math (`quantity × emission_factor`) is a deterministic physical calculation — ML must never touch it, or an auditable number becomes unaccountable and could hallucinate figures that regulators/consultants need to trust completely. ML earns its place **only** in the recommendation layer, where "which of several plausible interventions best fits this specific facility" is a genuinely ambiguous, multi-factor ranking problem — a good fit for a learned scoring model.

## 3. Exact ML Problem Type

**Ranking / Recommendation** — not classification, not regression in the traditional sense. We are not predicting a single label or a continuous physical quantity; we're ordering a candidate set of interventions per leak point by suitability.

**Practical framing:** a learning-to-score problem — predict a suitability score (0–100) per `(facility_profile, leak_point, intervention)` triple, then sort by score.

**Why this framing is appropriate:**
1. The output actually needed is an ordering, not a class label.
2. Multiple relevant signals (cost, CO₂ impact, fit, difficulty) need to be blended into one score — a regression-style scorer does this naturally.
3. It degrades gracefully to a weighted rule-based formula, which a pure classifier would not as naturally.

## 4. Input Features

| Feature | Type | Source |
|---|---|---|
| `industry` | categorical | Facility |
| `facility_size` | categorical | Facility |
| `leak_category` | categorical | ProcessInput aggregation |
| `leak_subtype` | categorical | ProcessInput |
| `leak_contribution_pct` | numeric | Leak-point calc |
| `leak_co2e_contribution` | numeric | Leak-point calc |
| `intervention_category` | categorical | InterventionLibrary |
| `estimated_cost` | numeric | InterventionLibrary |
| `expected_co2_reduction` | numeric | InterventionLibrary |
| `implementation_difficulty` | ordinal | InterventionLibrary |
| `industry_suitability` | categorical/boolean | InterventionLibrary.supported_industries |
| `region/energy_grid` (optional) | categorical | Facility |

## 5. Output / Target

`adoption_outcome` — a proxy label representing "how suitable/successful this intervention would be for this facility profile." For the hackathon this is necessarily **synthetic/curated**, not real historical adoption data (see §7).

## 6. Dataset Schema

**One training row =** `(facility_profile, leak_point, candidate_intervention, label)`

```
industry, facility_size, leak_category, leak_contribution,
intervention_category, intervention_cost, expected_CO2_reduction,
implementation_difficulty, industry_fit, adoption_outcome
```

**Example rows (illustrative structure only):**

| industry | facility_size | leak_category | leak_contribution | intervention_category | intervention_cost | expected_CO2_reduction | implementation_difficulty | industry_fit | adoption_outcome |
|---|---|---|---|---|---|---|---|---|---|
| plastic | medium | energy | 0.43 | energy | 55000 | 10 | high | true | 88 |
| plastic | medium | energy | 0.43 | energy | 15000 | 4 | medium | true | 67 |
| plastic | medium | materials | 0.21 | materials | 22000 | 5 | medium | true | 74 |

## 7. Dataset Strategy

- **Publicly sourceable:** emission factors (see `BACKEND_IMPLEMENTATION.md` §4/§7 sourcing note), general cost/CO₂-reduction ranges for common interventions (solar, recycled feedstock, etc.) from public sustainability/circular-economy references.
- **Must be curated by the team:** the intervention library itself (name, category, applicable leak types, industry suitability) — domain-knowledge assembly, not scraping.
- **Synthetic for the hackathon:** the `adoption_outcome` training labels — generated by combining the rule-based scoring formula (§10) with controlled random variation, producing a training set the ML model can learn a smoothed, blended version of. This **must** be clearly and repeatedly labeled as synthetic training data used to demonstrate the ML pipeline, never presented as real-world adoption outcomes.
- **Never do:** present synthetic adoption data as real SME behavior; claim emission factors are anything other than their actual public source.

## 8. Preprocessing

- Categorical encoding: one-hot for `industry`, `intervention_category`, `leak_category` (dataset is small — one-hot is safer/more explainable than target encoding).
- Numeric scaling for `estimated_cost`, `expected_co2_reduction`, `leak_contribution_pct`.
- Ordinal encoding for `implementation_difficulty` (low/medium/high → 0/1/2).
- Deduplication and handling of missing `industry_fit` values as part of cleaning.

## 9. Candidate Intervention Representation

Each candidate row is the cross product of one leak point with every intervention in `InterventionLibrary` whose `applicable_leak_types` and `supported_industries` match the facility's leak-point profile — this filtering happens **before** feature-vector construction, so the model never scores obviously irrelevant interventions.

## 10. Model Selection

**Gradient Boosted Trees** — e.g., `scikit-learn GradientBoostingRegressor` or a small XGBoost regressor — predicting the suitability score directly (a regression framing of the ranking problem, the simplest credible approach).

**Why this model is appropriate:**
- Tabular data, small/medium dataset (tens to low hundreds of curated rows).
- Mixed categorical + numeric features.
- Feature-importance explainability is needed for the judge-facing "why recommended" story.
- Standard, defensible choice for this data shape and size.

**Why deep learning is explicitly NOT justified:** the dataset is small, there is no sequential/image/text structure to exploit, and a boosted-tree model is both easier to explain to judges and easier to train reliably in hackathon time.

## 11. Training Pipeline

```
Curated + Synthetic Dataset
   ↓ Cleaning (dedupe, handle missing industry_fit values)
   ↓ Feature Engineering (encode categoricals, scale numerics)
   ↓ Train/Test Split (e.g., 80/20)
   ↓ Model Training (GradientBoostingRegressor)
   ↓ Evaluation (§13)
   ↓ Save Model (pickle/joblib, versioned filename)
```

## 12. Inference Pipeline

```
Facility Data → Deterministic CO₂ Engine → Leak-Point Ranking
   → Candidate Interventions (filtered by leak type + industry from InterventionLibrary)
   → Feature Vector Construction (facility + leak-point + intervention features)
   → ML Model → Suitability Scores
   → Sort Descending → Ranked Recommendations (returned via API)
```

**Example output (post-ranking):**
```
Leak Point: Diesel Generator (43% contribution)
1. Solar + Grid Hybrid ........ 91/100  ✓High contribution ✓Strong industry fit ✓High CO2 reduction ✓Acceptable cost
2. Battery Storage ............ 78/100  ✓High contribution ✓Moderate cost ✗Higher difficulty
3. Biodiesel Switch ........... 64/100  ✓Fast payback ✗Lower CO2 reduction vs. #1
```

## 13. Evaluation Metrics

Since this is a ranking problem, use ranking-appropriate metrics rather than classification accuracy:

- **Top-K relevance:** does the model's top-3 recommended interventions per leak point match the top-3 the rule-based formula (the domain-logic baseline) would pick? Report agreement %.
- **Ranking correlation:** Spearman's rank correlation between the ML-produced ranking and the rule-based baseline ranking on held-out rows.
- **Regression sanity check (MAE/RMSE)** on the held-out suitability score — a secondary/supporting metric only, since raw score error matters less than whether the ordering is sensible.
- **Explicitly avoid:** plain classification "accuracy" — there is no discrete class here, and using it would be a metric chosen to sound advanced rather than to measure the right thing.

## 14. Explainability

Every recommendation ships with an explanation checklist derived from the same features used to score it (e.g., ✓ High emission contribution, ✓ Strong industry fit, ✓ High CO₂ reduction potential, ✓ Acceptable investment). These flags are threshold-based on the underlying feature values (e.g., `leak_contribution_pct > 0.3` → "High emission contribution"), generated deterministically alongside the score — not a separate free-text generation step, so there's no risk of the explanation contradicting the score.

## 15. Rule-Based Fallback

**Always available**, ships first (Day 1–2), and is fully sufficient for a complete demo on its own if the ML model underperforms or fails to train in time.

**Formula:** a weighted scoring function combining normalized values of:
- CO₂-reduction potential (higher → higher score)
- Cost (lower, relative to facility size → higher score)
- Implementation difficulty (lower → higher score)
- Industry/leak-type fit (boolean gate — non-fitting interventions are excluded before scoring, not down-weighted)

**Output contract is identical to the ML path:** `{intervention_id, score, score_source: "rule_based", explanation_flags}` — the backend and frontend never need to know which path produced a given response.

## 16. Backend Integration / API-ML Interface

- `ml/inference/ranker.py` exposes one function: `score(facility_profile, leak_points, candidate_interventions) → List[{intervention_id, score, score_source, explanation_flags}]`.
- The backend's `recommendation_engine.py` calls this function; on any exception, missing model file, or timeout, it calls `rule_based_scorer.py` instead, using the identical signature.
- The model is loaded once at FastAPI startup (`main.py`), never per-request — this is tested explicitly on Day 2, not left until Day 3.

## 17. Handling Missing Data, Unsupported Industries, and Unseen Inputs

- **Missing feature values** (e.g., no region/grid data): the feature is imputed with a neutral default (e.g., median/mode from training data) rather than blocking scoring.
- **Unsupported industries** (outside the 3 MVP industries): the candidate-filtering step in §9 returns no candidates for that industry; the API responds with an explicit "industry not yet supported" state rather than a silently empty or wrong list.
- **Unseen leak-point subtypes:** if a subtype wasn't part of training, the model still scores it using its known categorical features (one-hot encoding maps unseen categories to an "other" bucket); if confidence is a concern, the rule-based fallback is used instead for that specific candidate.

## 18. Testing

- **Dataset validation:** schema check on load (correct columns/types), no nulls in required fields after preprocessing.
- **Model loading:** startup fails loudly (logged) if the model file is missing/corrupt, and the system automatically routes to rule-based scoring.
- **Prediction:** unit test that `score()` returns a list of the correct shape for a known facility/leak-point/intervention set.
- **Ranking:** verify top-1 recommendation is stable/sensible for the ABC Plastics demo scenario specifically, since this is what judges will see.
- **Fallback:** explicit test that forces an ML failure (e.g., mocked exception) and confirms the rule-based path returns a valid, identically-shaped response.
- **Edge cases:** zero candidate interventions (unsupported industry), a single leak point, a facility with no calculated emissions yet.
